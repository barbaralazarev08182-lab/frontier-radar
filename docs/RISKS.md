# 技术风险与待确认事项（RISKS）

## A. 技术风险

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | **arXiv 限流严格**（≥3s/req） | 论文采集慢，单次采集耗时长 | 采集器强制间隔；按类别分批；失败续跑不重头来 |
| R2 | **HF 限流未文档化** | 可能被 429 | 自我限流 ≤1 req/s；指数退避；记录 429 到 collection_runs |
| R3 | **GitHub 搜索结果上限 1000** | 漏掉长尾仓库 | 多查询词切片 + 按 `pushed_at` 窗口分批；不以 Star 排名为唯一入口 |
| R4 | **跨源去重难** | 同一项目在 GitHub/arXiv/HF 各一条 | 阶段 1 仅源内去重；跨源合并放阶段 2 |
| R5 | **AI 成本与延迟** | 大量条目逐条分析慢且贵 | 先评分筛选 Top-N 再分析；批量 prompt；缓存结果避免重复分析 |
| R6 | **冷启动无增长数据** | 首日 24h/7d 增长为空 | 动量维度中性 50 + 标注 cold-start；积累 7d 后自然恢复 |
| R7 | **复现难度为 AI 主观判断** | 可能不准 | 输出依据；低权重；保留 unknown 选项 |
| R8 | **Supabase 免费额度** | DB 大小 / 出站流量 / cron 数限制 | 控制历史快照保留期；定期归档；监控用量 |
| R9 | **Vercel Cron 免费版频率限制** | 可能无法高频采集 | 阶段 1 每日 1 次，免费版可满足；如需更高频改用 Supabase Scheduled Function |
| R10 | **原始 payload 体积** | raw_items jsonb 膨胀 | 仅存必要字段；可设保留策略；大文本截断 |
| R11 | **时间窗与口径** | "24h 增长"依赖快照连续性 | 用 `COLLECTION_TIMEZONE` 统一口径；缺日按 cold-start |

## B. 待确认事项（需用户拍板，进入阶段 1 前明确）

| # | 事项 | 默认假设 |
| --- | --- | --- |
| Q1 | **腾讯模型 API 具体型号与接入方式**（是否提供 OpenAI 兼容 endpoint？用哪个 SDK？模型 ID？） | 假设有 OpenAI 兼容 endpoint，待确认后调整 `src/lib/ai` |
| Q2 | **每日采集次数与时刻** | 每日 1 次，凌晨（Asia/Shanghai） |
| Q3 | **调度方案**：Vercel Cron 还是 Supabase Scheduled Function | 默认 Vercel Cron |
| Q4 | **个人兴趣画像**：六个大类（AI/ML/开源/Vibe Coding/产品设计/量化金融）的关键词与权重是否需要我先给默认稿 | 先给默认稿，用户审 |
| Q5 | **Top-N 阈值**：每日 AI 分析多少条（成本 vs 覆盖） | 默认 Top 30 |
| Q6 | **历史快照保留期** | 默认保留 90 天，更早的按月聚合 |
| Q7 | **是否需要阶段 1 就做跨源去重** | 否，阶段 2 |
| Q8 | **Supabase 项目是否已创建**（URL / service role key 由用户提供） | 待用户提供 |
| Q9 | **是否需要登录鉴权** | 阶段 1 不需要（个人使用，RLS 保护即可） |
| Q10 | **GitHub Token / HF Token / 腾讯密钥**由谁提供 | 用户提供，仅写进 .env（不入库不入 git） |
